# Release train

Releases bld together with the extensions it builds with, and optionally
RIFE2 and RIFE2/core, in the order their dependencies demand.

```bash
./bld release-train plan bld+rife2
```

## What this is, and what it isn't

This is the release script, run by the one person who can release these
projects, from a terminal, watching the output. That's the whole ambition.

So it keeps no state between runs, is not resumable, and never repairs,
rewinds or reconciles anything. Every phase runs from its start each time.
Its checks refuse and explain, they don't fix. When it stops halfway, read
the message, sort out the cause, run the phase again, which is cheaper and
more predictable than machinery that tries to work out what a half-finished
release left behind.

It doesn't police the workspace either. It refuses only where the mistake
would be public and permanent: publishing a version that is already out,
publishing something other than what was built, publishing from a checkout
whose push would then fail, releasing a build that depends on a snapshot,
and a simulated run that could reach the outside world. Everything else is
in the output for whoever is watching it.

Publishing is the only step that can't be undone, and the only one treated
as such: it asks first, and if it fails partway through the repositories it
publishes to, it says so and leaves the decision to you.

## What it releases

Every run releases bld and the extensions declared in
`release-train.properties`. Core and RIFE2 join through the shape:

| shape | releases |
|---|---|
| `bld` | bld and the extensions |
| `bld+rife2` | also RIFE2 |
| `bld+core` | also RIFE2/core |
| `bld+rife2+core` | all of them |

Members outside the shape are still put on the new bld, they just don't
get a release of their own. Followers only ride along for that.

## Why the order is what it is

Everything in a release needs something else in the release, so the order
comes down to which need can be satisfied from the local repository and
which can't.

* The bld blueprint names the RIFE2 version that generated projects depend
  on, and those projects resolve from Maven Central only. So RIFE2 has to
  be resolvable there before bld is published, and the blueprint can only
  name it once it is.
* An extension compiles against bld, and bld's wrapper resolves the
  extensions. That's a cycle: neither can be built from public artifacts
  before the other is out. It's broken by building against the local
  repository, which holds the whole release from the local phase onwards.
* bld is what names the extensions. A bld published before them would be
  tagged with a wrapper naming extension versions that aren't public, so
  anyone building bld from its own release tag would fail.

Which gives: the extensions, then core, then RIFE2, then bld.

That leaves one window, and it's the cheap one. An extension pom names bld
in compile scope, and resolving an extension reads that pom, so between an
extension's publication and bld's the new extension version can't be
resolved by anyone. It lasts as long as the rest of the train, the wait for
RIFE2 on Central included, so think hours rather than minutes. No published
artifact depends on those versions before bld is out: the blueprint names
them only then, and the poms of core and RIFE2 don't name them at all. What
the window does hold is source builds. The core and RIFE2 tags pushed during
it name the new bld and extensions in their wrappers, so a checkout of
either tag doesn't build until bld is public. Inside the train it costs
nothing, since every build that resolves a just released extension still
has the local repository in its wrapper.

## The phases

### plan

```bash
./bld release-train plan bld+rife2
```

Shows what each version becomes and what would stop a run.

### local

```bash
./bld release-train local bld+rife2
```

Everything happens on the machine. The steps for core and RIFE2 run only
when the shape includes them, the rest run every time:

1. core gets its version and is built. RIFE2 compiles core from its own
   checkout, so that one gets the same version
2. bld gets its version and is built with the previous bld, then published
   locally
3. every extension is pointed at the local repository, updated to the new
   bld and its own new version, built and published locally
4. bld is rebuilt with itself and the new extensions
5. RIFE2 is built with both and published locally
6. every member and follower is put on the new bld: the version and the
   extensions are pinned, the wrapper files are regenerated by the new bld
   itself, and everything is rebuilt, with the tests run for everything
   that gets released when `train.tests` is on
7. the blueprint is pointed at the new RIFE2 and bld is rebuilt, a project
   is generated and built against the local publications, and the blueprint
   is put back

Step 6 is what makes the commits that get tagged already coherent. The bld
distribution is in the local distribution directory by then, so the
repositories build with the new version before it is public.

The local repository stays in every wrapper through all of this, and in the
build files of the extensions. It has to: the phases that follow are
launched by those wrappers, and until the extensions are published there is
nowhere else for a wrapper to find them. Each repository loses it in the
run-up to its own release commit.

The blueprint is the last thing pointed at the new RIFE2 and the first thing
put back, because bld's own tests generate projects from it and resolve them
from public repositories. A blueprint naming a RIFE2 that isn't out yet fails
every one of those tests, so it names the new one only long enough for the
generated project to prove they fit together. The publish phase makes that
edit for real once RIFE2 is public.

Nothing has left the machine at this point, so this phase can be run as
often as needed.

### review

```bash
./bld release-train review bld+rife2
```

Shows what is waiting to be committed in every repository the release
touches, with the rewrites the phases made separated from whatever was
already there. A release commits everything a repository holds, so the
second group rides along with it.

It then lists what the local phase put in the local repository, which is the
preview of what `publish` uploads, and names any pom that depends on a
snapshot. Core isn't listed, it is compiled into bld and RIFE2 rather than
published on its own.

This only reads and refuses nothing, so it can be run between any two
phases.

### publish

```bash
./bld release-train publish bld+rife2
```

It starts by reading back what the local phase was supposed to establish:
the version files of bld, core and RIFE2, and each extension's own version
and bld dependency. Each project derives what it publishes from its own
sources while the tag and the confirmations come from the configuration, so
those have to agree. The wrappers aren't checked here, they still resolve
from the local repository at this point.

Then, per repository in the order above: take the local repository back out
of the wrapper and, for an extension, out of its build file, check that this
one repository is on the bld and the extensions being released, commit, tag
with an annotated tag, publish, and push the commit and the tag in one atomic
push. Before publishing it checks that the push would fast-forward, since a
branch that moved on independently would otherwise only surface once the
artifacts are already public. It asks before every publication and shows what
the release commit contains.

Publishing builds the project again, against a release that is still only in
the local repository, so the local repository goes back in for that build
alone and the commit that was just made is checked back out over it
afterwards. The release commit is the clean one, the build behind the
publication is not, and nothing of that reaches the artifacts: a published
POM carries no repositories.

After RIFE2 it waits until its pom and jar are both resolvable, then points
the blueprint at it and builds bld, with its tests when the train runs them.
Those are the tests the local phase had no way of running, since the RIFE2
they generate projects against has to be public. After bld is published it
waits for that too, so that converge doesn't tell everyone to use a version
that hasn't landed yet.

A repository whose release tag is already where it pushes to is skipped. The
tag goes out together with the release commit right after publishing, so it
is the thing that says a release is out, which is what makes rerunning this
phase safe after it stopped halfway. Skipping needs the checkout to be on
that same commit and clean; anything else is a question for you rather than
something to assume. A local tag of that version on another commit stops the
phase instead of being moved, and it is judged against the release commit, so
a correction made after a failed attempt can't leave the tag behind.

When core is released, RIFE2's own core checkout is moved onto the released
core commit right after, whether or not RIFE2 is part of the release, since
the two of them otherwise end up recording different cores. What each parent
repository *records* about its core is allowed to differ in the meantime:
publishing bld records the new one while RIFE2's update is still waiting for
the converge phase. What has to agree is the checkouts themselves, since
those are what gets compiled.

A publication is the one thing here that can't be undone. It publishes to
several repositories in one command, so if it fails, check which of them
already have the release before running the phase again. If publishing
succeeded and only the push failed, it says so and prints the push to run
by hand, running the phase again in that state would publish the same
version twice.

> **NOTE:** when the wait for a release doesn't see the artifacts, it asks
> every fifteen minutes whether to keep waiting. That's fine with somebody at
> the terminal and a trap for anything automated, which will happily answer
> yes forever.

### converge

```bash
./bld release-train converge bld+rife2
```

Commits and pushes what the release itself didn't: the members outside the
shape and the followers. It pushes every repository whether or not it had
something to commit, since a run that committed and then failed to push
leaves a clean repository whose commit never arrived. Ends by checking that
every wrapper is on the bld and the extensions being released, with nothing
left pointing at a local build.

It doesn't audit the workspace beyond that. Content inside a submodule, for
instance, makes the repository around it look modified while nothing stages,
so it says "nothing to commit, only content inside a submodule differs" and
moves on, you can see it and decide.

## Configuration

`release-train.properties` in the bld project directory declares all the
versions, whether a given run releases them or not:

```properties
train.core.version=1.10.0
train.rife2.version=1.10.0
train.bld.version=3.0.0
train.extension.bld-antlr4=1.4.4
train.extension.bld-archive=0.6.4
train.extension.bld-tests-badge=1.6.4
train.extension.bld-junit-reporter=1.2.0
train.followers=rife2-bld-hello
train.releases.repository=
train.simulate=false
train.tests=false
```

Extensions and followers are checked out next to the bld project
directory, every one of them has to be there. Versions have to be plain
`major.minor.revision` ones, since they are written into source as
`version(3, 0, 0)` literals.

`train.tests` decides whether the builds in the train also run their test
suites, and defaults to running them when it isn't declared. CI runs every
suite on every push, so a release that follows a green CI run doesn't need
them again, and they are most of what the local phase spends its time on.
The generated project runs its tests either way, since that is the one
thing no CI run covers: it is what shows the publications fit together.
`plan` says which way a run is configured.

## Rehearsing it

The whole thing can be run end to end without anything reaching the outside
world. Three things would:

| reaches out | redirected with |
|---|---|
| `bld publish` | `bld.repo.<name>` properties per repository |
| `git push` | a local bare clone as the remote |
| the wait for the release | `train.releases.repository` |

Set `train.simulate=true` and the phases refuse to start unless
`train.releases.repository` is an absolute path or a URL on this machine,
every `bld.repo.*` destination every repository could publish to is one of
those, and every URL a push would reach is one. A remote it can't read counts
as a problem, not as a pass.

A directory works as the destination, but publishing to one skips the upload
path entirely: bld copies the files and doesn't generate checksums or
signatures for a repository it considers local. A maven repository on the
loopback interface exercises the real path instead, the PUT per file, the
credentials, the checksums and the signatures. Reads on it should be open and
only writes authenticated, the way a public repository behaves, since the wait
for the release checks what a consumer can reach rather than what the releaser
can.

Two things a rehearsal can't reproduce. Maven Central will never hold the
release, so bld's own tests that generate projects from the blueprint can't
resolve it, and the blueprint has to offer the local repository as well for
those to pass. And the wrappers, the version files and the tags are the real
ones, so a sandbox is worth throwing away and rebuilding rather than reusing.

### Setting up the sandbox

`rehearsal/rehearse.sh <directory> [port]` builds one and prints the phases
to run from it, next to the `RepositoryServer.java` it starts. What it has
to do, and what any other way of doing it has to cover:

* clone every member, extension and follower, each with a bare clone next
  to it as its remote, so a push stays local
* point the core submodule of bld and of RIFE2 at that bare clone, and put
  bld's on a branch, since core is released from there and a push from a
  detached HEAD does nothing. RIFE2's follows on its own. Cloning a
  submodule from the file system needs `-c protocol.file.allow=always`
* redirect every publication name declared by a build file or by
  `~/.bld/bld.properties` to the loopback repository, in the
  `local.properties` next to each build file, and commit that, since
  `local.properties` is tracked. Deriving the names from the projects beats
  assuming them, though a missed one stops the run rather than slipping out:
  a name that resolves to nothing fails the build
* add the loopback repository to the wrapper properties of each repository,
  next to the ones already there, so the extensions released during the
  rehearsal resolve while everything else keeps coming from where it did
* build the example projects that extension tests read reports from, which
  a worked-in checkout has and a fresh clone doesn't
* offer the loopback repository in the blueprint as well, so generated
  projects can resolve a RIFE2 that Central will never have
* set `train.releases.repository` to the loopback repository and
  `train.simulate=true`

It takes the members from the directory the bld project sits in, and reads
their committed state, so anything uncommitted in a checkout stays out of
the rehearsal. A dependency that is still a snapshot stops the run the way
it stops a release, so those have to be released and pinned first, in the
sandbox or for real.

### What still touches the machine

The local phase publishes bld, the extensions and RIFE2 into
`~/.m2/repository`, and the bld distribution ends up in `~/.bld/dist`,
under the versions being released. That is what lets the repositories
build on the new bld before it is public, and it is what a rehearsal
leaves behind. Remove it afterwards so a real release doesn't build
against it, from the bld project directory so the versions come from the
configuration:

```bash
while IFS='=' read -r key version; do
    case $key in
        train.bld.version)   artifact=bld ;;
        train.rife2.version) artifact=rife2 ;;
        train.extension.*)   artifact=${key#train.extension.} ;;
        *) continue ;;
    esac
    directory=~/.m2/repository/com/uwyn/rife2/$artifact/$version
    if [ -d "$directory" ]; then
        rm -rf "$directory" && echo "removed  $directory"
    else
        echo "absent   $directory"
    fi
done < release-train.properties
bld_version=$(grep '^train.bld.version=' release-train.properties | cut -d= -f2)
find ~/.bld/dist -maxdepth 1 \( -name "bld-$bld_version.jar" -o -name "bld-$bld_version-sources.jar" \) \
     -delete -print | sed "s/^/removed  /"
```

It says what it removed and what wasn't there, and it can be run twice.


The generated project resolves its own dependencies from the public
repositories, so a rehearsal downloads what any build downloads. It never
publishes anything.
